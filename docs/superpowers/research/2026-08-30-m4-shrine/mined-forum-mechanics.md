# M4 博丽神社：成熟论坛机制的先例研究与取舍

2026-08-30 · 调研材料，**不是决定**。正式范围见 `docs/superpowers/plans/`。

对象：NGA · Discourse · 百度贴吧 · V2EX · Reddit · linux.do · 2ch/5ch · phpBB/Discuz 世代。
产出**不是功能清单，是取舍判断**：每条机制回答"解决什么问题 / 现在有用吗 / 不做的代价"。

---

## 0. 一页结论

上线时论坛的真实状态：**主题数 ≈ 资源数（每个资源自动挂一个讨论主题），人写的主题数 ≈ 0，日活 ≈ 站长 + 个位数**。
在这个状态下，成熟论坛的机制里**大约七成是负价值或零价值**——它们全都是为"内容太多"设计的，而这里的问题恰好相反。

| 分类 | 条数 | 一句话判据 |
|---|---|---|
| **M4 必须有** | 18 | 缺了它①资源站→论坛的供血管道断掉，或②反馈回路合不上，或③solo 站长被人肉运营压垮 / 站会出事 |
| **M4 之后再说** | 16+2 | 它解决的是**规模问题**。规模为 0 时收益为 0，而实现全是 additive，且有了真实数据才知道怎么调 |
| **永远不做** | 6 | 它的代价随社区变大而变大，收益却从来不属于这个平台 |

一条贯穿全文的分类法：

> **规模型机制 vs 形状型机制。**
> 规模型（热度排序、子版块、未读标记、勋章、全文搜索）**晚做比早做便宜**——那时才有分布数据可调参，且实现是纯 additive。
> 形状型（对外 URL、用户 handle、通知的产生点、内容的删除语义）**晚做要动已发出的链接或做数据迁移**。
> M4 的全部注意力应该花在形状型的三四件事上，规模型的一律推。

M3 那条方法论纠正在这里同样成立且更强：库里没有数据时"以后要迁移"不成立，`rm -rf drizzle && generate && migrate` 是零成本的。**真正不可逆的只有已对外发出的 URL / slug 和法律留痕。** 见 §6。

## 1. 判据：三个冷启动失败模式

不列判据就无法区分"必须有"和"看起来很必须"。论坛冷启动只有三种死法，"必须有"必须对着其中之一：

**失败模式 A —— 来了没东西看，不再来。**
论坛的库存价值为零，而资源站有库存。对策全部是"把资源站的活动引流进论坛的可见面"。这是"资源评论 = 论坛帖"这条已批准决策的全部意义，但**决策只说了数据同源，没说视图怎么摆**——摆错了它一分钱供血也供不出来（§3.1、§3.2）。

**失败模式 B —— 发了帖没人理，不再发。**
5 个人的论坛里，首帖 0 回复是常态，不是异常。对抗手段是把"给出反馈"的成本降到一次点击（点赞），并保证反馈**被发帖者看见**（通知）。缺任何一半，回路都合不上：没有点赞，反馈不会发生；没有通知，反馈发生了但发帖者不回来看，等于没发生。

**失败模式 C —— 站长被垃圾内容压垮，关站。**
这条与社区规模无关，只与"公网上有一个开放的写端点"有关。上线第一天就会被扫。solo 运营下，一夜之间三千条 SEO 垃圾帖的人肉清理成本，足以让站长直接放弃这个模块。

**"必须有"的判据就是：它对着 A、B、C 之一，且没有更便宜的替代品。**
不对着任何一条的，无论多标准、多常见，一律推到"之后再说"。

第四条需要单独说：**冷启动最大的杠杆根本不是功能**。Discourse 官方冷启动手册的第一条是"创始人先自己发够内容并回复每一个帖子"。六个空版块各钉一条站长写的引导帖 + 站长回复前一百条帖，其效果大于本文清单里任何一项功能。这件事成本为零、不需要代码，但**它需要置顶功能存在**（§3.7）——这是置顶进"必须有"的真实理由。

## 3. M4 必须有（18 条）

### 3.1 版块：六个、扁平、且**不作为默认视图**

**解决什么** 内容分流 + 预期设定（"这里该发什么"）。

**现在有用吗** 版块本身有用，但用途不是分流——0 帖不需要分流——而是**给一个空论坛一个"这里应该有什么"的骨架**。六版块已产品批准，不推翻。

但要指出一个不对称，它直接影响该开几个：**关掉一个版块 = 一条对外死链（不可逆的那一类）；新开一个版块 = 零成本 additive。** 按不可逆性判据，正确方向永远是少开。这与"初始六版块"有张力，处理办法不是推翻决策，而是：**六个全开，但此外一个都不再开，并且不要把版块目录当默认落地页**。

**默认视图必须是全站「最新」信息流**（按 `lastPostAt` 倒序），版块降级为筛选器 / 侧栏导航。理由直击失败模式 A：六个各 0 帖的版块并排展示，读到的信息是"这地方是死的"；而一条混合了资源讨论的最新流，读到的是"这里有人在动"。同一份数据，两种摆法，冷启动结果完全不同。NGA/贴吧的版块目录首页是**在每个版块日均三位数帖量之后**才成立的排版。

**不做的代价** `board` 表建议真建（版块名要三语 jsonb、要排序、要描述，与 `tag`/`resource_category` 同构），因为**版块 slug 是对外 URL**。硬编码在 Paraglide 里也能跑，但改名/加版块要动代码部署。这是唯一一处我建议"多建一张表"的地方，代价一张 5 列的查找表。

### 3.2 资源讨论主题注入全站最新流（本项目独有，先例里没有对应）

**解决什么** 这是"资源评论 = 论坛帖"这条已批准决策真正兑现价值的地方。先例里没有完全对应的：NexusMods 的 mod 评论区与论坛是**分开的**，Steam 创意工坊评论区独立，Discourse 的 discourse-topic-embed 是把论坛嵌进外站而不是反过来。所以这条没有现成答案，必须自己判断。

**现在有用吗** 这是**整条供血管道**，M4 的第一优先级。但它有两个必须现在回答的子问题，答错了管道就是通向沟里：

**子问题 1：资源讨论主题属于哪个版块？**
建议**不属于任何版块**（`boardSlug` 保持 null，靠 `kind='resource'` 区分），但出现在全站最新流里，带一个可辨识的资源徽章。
- 若按资源 kind 映射进版块（game→弹幕研究所、music→音乐堂），六个版块会立刻被资源评论淹没，版块的定位被稀释，人写的主题反而看不见——这恰好毁掉了版块存在的唯一理由。
- 全站最新流的职责本来就是"任何地方有人说话都在这里"，资源讨论天然属于它。
- 与 `topic` 表现有形状完全吻合，一行 schema 都不用改。

**子问题 2：资源讨论主题在 /shrine 下有没有自己的 URL？**
建议**没有**：`/shrine/t/:id` 对 `kind='resource'` 的主题 **301 到资源页的评论区锚点**，规范 URL 唯一地落在 `/kourindou/:slug`。
- 一份数据两个可索引 URL = SEO 重复内容 + 用户困惑（"我刚才在哪看到的"）。
- 301 而不是 404：论坛的最新流里那条目直接链资源页即可，301 只是给手改 URL 和外部链接兜底。

**不做的代价** 不注入最新流，则 M4 上线当天 /shrine 首页真的是空的，失败模式 A 直接命中。这条没有"以后补"的选项——它决定的是上线那一周的观感，而冷启动只有一次。

### 3.3 楼层制 + 引用（不做树形）

**解决什么** 楼层号解决"指认某一句话"（"你看 42 楼"）；引用解决"在读不懂的对话里恢复上下文"。

**现在有用吗** 形态已被 M3 定死且定对了：`post.floor` 顺序编号为主，`parentId` 只用来渲染引用关系。**M4 要做的判断是不要把 parentId 渲染成树。** Reddit 式树形的价值在于一个主题下数百条并行子讨论的可读性——那是规模型收益；而它的代价是**当场破坏楼层号心智**（树里没法说"42 楼"），且移动端缩进层级是灾难。楼层 + 引用块是 NGA/贴吧/V2EX/linux.do 的共同选择，也是产品文档明确的心智。

引用有一个需要现在决定的细节：**被引内容是发帖时快照进 `bodyMd`，还是渲染时按 `parentId` 现查？**
- NGA 是快照（被引楼后来被编辑，引用块不变）。
- 建议**现查**，被引楼被软删则渲染成"该楼已删除"。理由是治理成本：solo 站长删掉一条违规内容时，绝不希望它以快照形式散落在十个引用块里删不干净。快照方案会把一次删除变成十次搜索替换。

**不做的代价** 引用的实现成本近乎为零（Markdown `>` 块 + 已有的 `parentId` + 渲染时一次查询），而没有它，楼层制的长贴完全读不懂。这是"零成本 × 高收益"，没有推的理由。

### 3.4 @提及 + 用户 handle（**形状型，不可逆**）

**解决什么** 把特定的人拉进对话——它是通知的第二个产生点，而通知中心是产品已批准的 M4 内容。

**现在有用吗** 有用，但真正的工作量不在 @ 本身，在**它的锚点**：`user.name` 目前不唯一、不可打字（可以含空格和 emoji）、且随时可改。@提及需要一个**稳定、唯一、可打字**的 handle，个人主页 URL（`/u/:handle`，产品文档承诺的"个人主页聚合"）需要同一个东西。

**这是 M4 三件不可逆决策之一**，因为 handle 一旦出现在对外 URL 里就再也改不动了（§6.2）。而 `/shrine` 和 `/u` 现在都还是空的，这是唯一的窗口。

范围要卡紧：M4 做（a）handle 字段 + 唯一约束 + 注册/首次设置流程、（b）编辑器里的用户名补全、（c）发帖时解析 `@handle` 落通知。**不做**改名历史、不做 @机器人、不做群组提及。

**不做的代价** 推迟 @ 本身，通知中心就少一半供给（失败模式 B）。推迟 handle，代价是不可逆的——等到有了 `/u/:name` 或帖子正文里已经存了 `@某个显示名` 再改，就是数据迁移 + 死链。

### 3.5 点赞：单向，**不做踩**

**解决什么** 把"给出反馈"的成本从"写一段话"降到"点一下"。

**现在有用吗** **这是对抗失败模式 B 的上半段，冷启动论坛最重要的机制之一。** 判断依据要说硬：5 人在线的论坛里，发帖者收到 3 个赞和收到 0 条回复，是完全不同的留存结果；而让这 3 个人各写一段回复，是不会发生的。Discourse 和 linux.do 把 ❤️ 放在最显眼处不是装饰。

形态必须是**单向点赞（Discourse / linux.do），不是 upvote/downvote（Reddit / HN）**：
- 踩在小社区是纯毒药——被踩一次是全站可见的社死，而 5 个人的社区里踩你的人你认得出是谁。
- 踩的唯一正当价值是内容过滤排序，而内容量为 0 时不需要过滤。
- 不对称性：以后加踩是 additive（计数列写负数），去掉踩不是（用户已经承受过了）。

**不做的代价** 一张与 `favorite` 完全同构的复合主键表 + 一个冗余计数列，M3 已有先例，成本极低。而没有它，失败模式 B 无解。

**多种 emoji 反应不做**（§4.9）：那是"社区已有文化"之后的表达工具，0 帖时它只是把一个按钮变成一个需要选择的菜单。

### 3.6 隐式订阅 + 站内通知中心

**解决什么** 失败模式 B 的下半段：让反馈**被发帖者看见**。产品文档已批准"通知中心（回复 / @ / 订阅 / 审核结果）"。

**现在有用吗** 有用，且这里有一个非做不可的设计判断：**订阅必须是隐式的**。
- 显式"关注此主题"按钮 = 一个要学习的新概念 + 一次点击，冷启动期没人会用。
- 隐式订阅（你发的主题、你回复过的主题自动订阅）是 Discourse / Reddit / linux.do 的默认行为。
- **没有隐式订阅，通知中心就只剩"回复我的楼层"和"@我"两种事件，冷启动期日均条数是 0。一个红点从不亮的通知中心是负资产**——用户学会了不看它，等到真有通知时也不看了。

四类事件够了：① 我的主题被回复 ② 我的楼层被回复 ③ @我 ④ 我订阅的主题有新回复。第⑤类"审核结果"来自 M3 的资源审核（`user_profile` 已有载体），顺手接上。

要一起做的三件小事，漏了会立刻变成投诉：
- **自己触发的不通知**（自己回自己的主题）——M3 的 `self_action_forbidden` 是同一种思维。
- **同一楼层的多个事件去重**：一楼同时"@我"且"回复我"，只出一条通知。
- **可退订（mute 一个主题）**——冷启动期不会有人被淹，但一旦有热闹主题就是紧急需求，而它只是订阅表上一个布尔列。

范围要卡紧：**只做站内 + 一个未读计数徽章，不做邮件**（§4.10）。已读语义只做"打开通知页 → 全部已读"，用 `user_profile` 上一个 `notificationsSeenAt` 时间戳即可，通知行上连 `readAt` 都不必有（逐条已读是 additive）。

**不做的代价** 订阅需要一张极简的表（topicId + userId + source + muted）。不做通知，失败模式 B 无解，且推翻了已批准的产品决策。

### 3.7 置顶（不做加精）

**解决什么** 置顶：让版规、公告、引导帖不被新帖冲下去。加精：从大量内容里标记优质，是**筛选**机制。

**现在有用吗**
**置顶要做**，但理由不是对抗信息流冲刷（没有冲刷）——而是**它是 §1 那个"最大杠杆"的载体**：六个空版块各钉一条站长写的"这个版块发什么 / 从这三个话题开始"，是 solo 站长唯一的零成本内容注入手段，也是把空房间变成有主人的房间的唯一办法。

**加精不做。** 加精是从 N 条里挑 top 5% 的操作，N=0 时它标记不出任何东西；更要命的是它一旦存在，站长就欠下了一份"持续评选"的运营债——而这个平台的全部前提是**低人肉运营**。

实现建议 `topic.pinnedAt timestamptz`（null = 未置顶）而不是 boolean：多条置顶时排序确定，且自带"何时置顶"的审计信息。排序变成 `ORDER BY pinned_at DESC NULLS LAST, last_post_at DESC`（注意现有的 `topic_board_last_post_idx` 需要跟着调）。

**不做的代价** 一列 + 一个 staff 端点。加精以后补也是一列（`featuredAt`），零成本。

---

### 3.8 锁帖（含**资源下架时自动锁**）

**解决什么** 终止已失控的讨论，但保留内容不删。

**现在有用吗** 有用，但理由不是"讨论失控"（没有讨论），而是两条别的：

**理由一：它是删帖的替代品。** solo 站长处理争议内容时，"删"是唯一会造成不可逆社区反感的动作。锁帖是可逆的、温和的、留证的中间档。M3 已经有软删和 `moderationLog`，锁帖补上治理光谱中间那一格，让站长在"忍着"和"删了"之间有第三个选择。

**理由二（这条是硬需求，现在就存在）：资源被下架 / 软删时，它的讨论主题必须自动锁。** 否则会出现"资源已经 404 了，评论区还能继续发新楼"。这是"一份数据两个视图"整合带来的必然后果，M4 不处理就是个现成的 bug——不是"以后补"的问题。

**不做的代价** `topic.lockedAt` 一列 + 写路径上一次白名单判断（注意 CLAUDE.md 的铁律：写 `lockedAt is null` 这种正向条件，别写反向排除）。

### 3.9 频率限制 + 新账号外链禁令（**M4 最不能省的一条**）

**解决什么** 挡自动化垃圾。

**现在有用吗** **这是全文我最确定的一条，而它的理由与社区规模完全无关：公网上一个开放的写端点会被扫，不管你有几个用户。** 上线第一天就会有 bot 注册并发 SEO 垃圾链接。这对着失败模式 C：solo 运营下，一夜之间三千条垃圾帖的人肉清理成本足以让站长放弃整个模块。

`rate_limited` 错误码在 M3 就写进 `errors.ts` 了但没有实现——说明这条早有预期，M4 必须补上。redis 已经在（gensokyo 占 db1），计数器是现成的。

三件事按性价比排序：
1. **新账号发帖不允许含外链**（或含链接则不发布、进队列）。这是 Discourse 的 TL0 规则，**性价比最高的一刀**——SEO 垃圾的全部载体就是链接，挡住链接，垃圾发了也没有收益，spam 会自己走开。
2. **每用户发帖频率上限**（如 30 秒一帖 + 每小时 N 帖），新账号更严。
3. **同内容重复发布检测**（相邻两帖正文完全相同直接拒），三行代码。

**不做的代价** 这条没有"以后补"的选项：等到需要补的时候，库里已经有三千条垃圾和一堆被污染的搜索索引，而清理是人肉的。

---

### 3.10 Markdown 渲染与净化（安全，不是产品机制但必须在清单里）

**解决什么** 产品文档要求"Markdown + 图片 + 表情 + @提及 + 引用"。而 `bodyMd` 目前是裸文本渲染——M4 加渲染器的那一刻，就打开了全站最大的 XSS 面。

**现在有用吗** 渲染器是产品要求，净化是它的不可分割部分。要点：
- **白名单标签与属性**，不是黑名单。原始 HTML 直接丢弃（不要试图"清洗"它）。
- 链接协议白名单：只放 `http:` / `https:`（M3 的 `safeUrl` 已经是这个模式，可直接复用思路）。`javascript:` / `data:` 一律拒。
- 图片：站内 MinIO 与站外热链的策略要现在定。建议**只允许站内 MinIO 的图片**（走已有的 `/api/uploads/image` 代理），外链图片一律不渲染成 `<img>`——外链图会泄露访问者 IP 给第三方、会失效、会被换成别的东西。这也与 CLAUDE.md 的存储分流约定一致。
- 净化必须**在渲染的那一侧**做（web），且服务端也要存原文 `bodyMd`——已有形状是对的。

**不做的代价** 没有净化就是 XSS，这条不需要论证成本收益。

---

### 3.11 硬词表（20 词量级，法律红线）

**解决什么** 自动拦截明确违禁的内容。

**现在有用吗** **只做最小的那一档**：一份很短的硬拦截词表（法律红线相关），命中即拒绝发布并返回 `validation_failed`。solo 站长不可能 7×24 盯着，而某些内容不能存在于库里，这条是纯风控。

**明确不做的三档**（这是本条真正的判断）：变体绕过检测、命中后替换成 `***`、分级/可配置词库。理由：大词库会持续误伤——东方圈的角色名谐音、日文汉字、社团名——而每一次误伤都是一次人肉申诉处理，恰好是要避免的人肉运营。**一个 20 词的表几乎不误伤；一个 2000 词的表天天误伤。**

顺带一条：**AI 内容审核比词表更适合这个场景**（"solo + AI 运营"是明确前提），但它推到之后（§4.12）——理由是它的收益随帖量线性增长而工程复杂度是恒定前置的，0 帖时每天跑 0 次。

**不做的代价** 词表放代码常量或 `siteConfig`（kv 表已在），换实现零成本。

### 3.12 举报（接线，非新建）

`report.targetKind` 已支持 `'post'`，`createReportSchema` 已含 `z.enum(['resource','post'])`，`/dash/reports` 后台已在。M4 只需要在楼层上挂一个举报入口，并让处理动作能对 post 生效（软删 / 锁主题）。**成本近零，收益是治理闭环的完整性**——产品文档明确"举报-处理-申诉闭环两模块共享"。

### 3.13 新人限制：**资源先审，帖子先发**

**解决什么** 用信任梯度替代人工审核，这是"低人肉运营"架构的核心。

**现在有用吗** 载体已在（`userProfile.approvedResourceCount` / `strikeCount` / `TRUST_AUTO_PUBLISH_THRESHOLD`），M4 要做的是**决定论坛侧的策略**，而这里最重要的判断是**两个模块共享信任等级的数据，但不共享策略**：

| 动作 | 策略 | 理由 |
|---|---|---|
| 新账号发资源 | **先审**（M3 已实现） | 版权是生死线，一条侵权资源的代价是法律级的 |
| 新账号发帖 / 回帖 | **先发后审** | 帖子先审在 0 帖时意味着站长要 7×24 守队列才有对话，而"回复延迟 6 小时"的论坛没有人会用。垃圾的代价远小于对话死掉的代价 |
| 新账号发含外链的帖 | **挡住**（§3.9） | 挡住 spam 的收益，且不阻断正常对话 |
| 新账号发新主题 | **不挡** | 这在冷启动期是自杀——唯一的新用户来发第一个主题，被拦住了 |

还有一个真问题要点出但不急着定：`approvedResourceCount` 目前**只由资源审核递增**，所以一个只逛论坛的用户永远升不了级。M4 需要给论坛侧一个升级路径（一个计数列 / 账号年龄），但**要防止造出刷帖升级的激励**——建议门槛保持单级、粗糙（如"`strikeCount === 0` 且（资源通过 ≥3 或 账号年龄 ≥7 天）"），不要做多级信任。**多级信任等级是 Discourse 的复杂度大头，它需要一个活跃社区来校准，而这里没有。**

### 3.14–3.17 成本近零、顺手做的四条

| 机制 | 判断 |
|---|---|
| **本地草稿**（localStorage，按 topicId+userId 键） | **要**。服务端草稿的价值是跨设备续写（重度用户需求，冷启动没有重度用户）；而"刷新页面内容没了"是**每个第一次发帖的人都可能撞上的**，冷启动期损失一个首帖代价极高。纯前端几十行，用更便宜的东西满足同一个真实需求。服务端草稿以后补是 additive（§4.14） |
| **主题标题搜索** | **要**，一条 SQL（或直接进已有的 Meili 索引）。楼层全文搜索推（§4.8） |
| **"已编辑"标记** | **要**，`post.updatedAt` 已存在，前端显示"编辑于 X"即可。**不设编辑时间窗口**——透明比限制便宜，solo 站长没有能力处理编辑争议。完整的 `post_revision` 历史表推（§4.4） |
| **版主 / 站长的可见标识** | **要**。这不是游戏化等级（§5.5），是**权威标识**：用户需要知道谁的话代表官方。`userProfile.role` 已在，渲染一个 badge |

### 3.18 东方表情（shortcode 固定表）

产品文档明确列入内容形态。**要，但用最小实现**：一组固定的静态图（`:reimu_smug:` 之类的 shortcode → `<img>`）+ 一个选择器。**不做**用户上传表情、不做表情包管理后台、不做表情市场。

它值得单独列出来的理由：这是清单里少数几个**冷启动期就有价值的"装饰性"机制**——它让一个空论坛看起来是"东方众的地方"，而不是"一个通用论坛模板"。对一个有强烈视觉文化的社群，身份认同的价值密度高于通用论坛。成本是一张静态映射表 + 一个渲染插件。

## 4. M4 之后再说（16 条，全部 additive）

共同点：**它们解决的都是规模问题**，规模为 0 时收益为 0；且晚做往往更便宜，因为那时才有真实分布可以调参。

| # | 机制 | 解决什么 | 为什么现在没用 | 以后补的代价 |
|---|---|---|---|---|
| 4.1 | **子版块** | 单版块内容过大后的二次分流 | 六个版块每个 0 帖，再切一层就是 24 个空房间。**空房间比没房间更劝退** | `board.parentSlug` 一列，additive |
| 4.2 | **加精 / 精华** | 从大量内容里标记优质 | N=0 时标记不出东西；且带来"持续评选"的运营债，与低人肉运营前提冲突 | `topic.featuredAt` 一列 |
| 4.3 | **主题分类与标签** | 版块内二次分类（NGA 分区 / Discourse tag / V2EX node） | 同子版块，规模型。平台已有 `tag` 表（含 work/convention 维度），真要打标签时直接复用 | `topic_tag(topicId, tagId)` 一张关联表 |
| 4.4 | **编辑历史表** | 防"发了争议言论偷偷改掉"；争议时的证据 | 价值随社区规模与争议密度增长，0 帖时为 0。"已编辑"标记（§3.16）已覆盖 90% 的透明度需求 | `post_revision` 一张表，纯 additive |
| 4.5 | **主题收藏 / 书签** | 私人"稍后看" | 0 帖时没有值得收藏的东西；且"收藏"的心智已被资源站的 `favorite` 满足。**这不违反产品文档**——文档里的"收藏聚合"指的是资源收藏，M3 已有 | 与 `favorite` 同构的一张表 |
| 4.6 | **未读 / 新帖标记** | 回访时定位"上次之后有什么新的" | **清单里性价比最差的一条**：实现最复杂（每用户每主题一行读位置，写放大严重，Discourse 最复杂的子系统之一）× 冷启动价值最低（一眼扫得完全站）。替代品是"最新流 + 相对时间"，成本是一个排序 | `topic_read(topicId, userId, lastReadFloor)`，表会很大但那时才有必要 |
| 4.7 | **热度排序算法** | 从大量主题里浮出值得看的（HN `score/(age+2)^1.8`、Reddit hot） | **热度算法的作用是"抑制"**——把太多内容压下去。0 帖时需要的是"放大"：任何有人说话的主题都应该被顶上来，即 `lastPostAt` 倒序（NGA 的默认排序）。而且没有真实数据无法调参 | 排序是查询层的事，零成本 |
| 4.8 | **楼层全文搜索** | 在历史内容里找答案 | 需要把 `post` 送进 Meili：一条新索引管道 + 软删/私有内容的权限过滤 + 中文分词调优。标题搜索（§3.15）先顶着 | 索引管道 additive，`reindex.ts` 已有骨架 |
| 4.9 | **多种 emoji 反应** | 更丰富的低成本表达 | "社区已有文化"之后的工具。0 帖时它把一个按钮变成一个需要选择的菜单 | 反应表加一个 `kind` 列，`default 'like'` |
| 4.10 | **邮件通知** | 把不常回访的用户拉回来 | **这条有真实张力**：冷启动用户确实不天天回访，邮件是唯一的召回通道。但仓库里**没有任何邮件基础设施**（无发信、无模板、无退订、无送达率处理），而三语模板 + 退订闭环的工程量与整个站内通知相当。判断：先站内，观察到"有通知但用户不回来"的证据后再上 | 一条新管道，但通知表本身不用改（**不要预留 `emailedAt` 列**，那是标准的 YAGNI 预留） |
| 4.11 | **私信** | 一对一沟通 | 三条：①私信是**骚扰的主要通道**，且骚扰是 solo 站长最难处理的投诉——他看不到内容，只有双方说辞；②冷启动期的一对一需求可由"帖子里 @对方"覆盖；③真做它要一整套（会话、已读、拉黑、举报私信、站长能否查看私信的隐私政策）。**工程量最大 × 收益最小**。权利人联系站长的真实需求已由 `takedownEmail` + 静态页覆盖（M3 决策） | 完全 additive。但补的时候**必须同时补拉黑与举报，否则不要上线** |
| 4.12 | **AI 内容审核管道** | 自动分流可疑内容进队列 | 收益随帖量线性增长，工程复杂度（异步管道、重试、误判申诉）恒定前置。0 帖时每天跑 0 次。硬词表（§3.11）先顶着法律红线 | 异步管道 additive；`moderationLog` 已能记录机器决策 |
| 4.13 | **勋章 / 成就** | 游戏化激励 | 激励机制在没有活动的社区里激励不出东西；且勋章需要持续设计与颁发（又一笔运营债） | 一张表，additive |
| 4.14 | **服务端草稿** | 跨设备续写 | 重度用户需求。本地草稿（§3.14）覆盖了真正致命的那个场景 | 一张表 |
| 4.15 | **相似主题提示**（发帖前 Discourse 式实时提示） | 减少重复主题 | 冷启动期是**负价值**：提示永远为空，还多一次请求和一次视觉干扰 | 查询层，零成本 |
| 4.16 | **主题移动版块 / per-board 版主** | 归类纠错 / 分权治理 | 六个版块一个站长，per-board 版主是 0 个人的调度问题。移动主题看着是一个 UPDATE，但要配审计留痕 + 通知作者才算做完 | `board_moderator` 关联表；移动走已有的 `moderationLog` |

另外两条顺带定掉：
- **帖内投票（poll）**：不做。5 人社区的投票没有统计意义，而它是一个完整的子系统（选项、多选、截止、改票、结果可见性）。
- **主题短序号**（NGA/V2EX 式可口头传播的递增 id）：不做。这是社区文化成熟后的诉求，那时加一列 `bigserial` 回填是 additive，且旧的 uuid URL 仍能解析（只需保留 301）。现在做就是标准的"预留"。

## 5. 永远不做（6 条）

判据不同于 §4：这些不是"现在不划算"，而是**代价随社区变大而变大，收益却从来不属于这个平台**。

### 5.1 @全体 / @everyone
它唯一的正当场景是全站公告，而这个场景已经被**两个更好的载体**覆盖：`siteConfig.announcement`（三语，M3 已实现）和站务版块的置顶。一旦这个按钮存在，它就是"一次权限配置错误 = 全站骚扰"的常备风险，且是 Discord 世界里持续的运营麻烦来源。**已经有正确答案的问题，不需要第二个更危险的答案。**

### 5.2 匿名发帖
四条理由，任何一条单独都够：
- 它与信任等级体系**直接冲突**——匿名内容无法归因，无法计入信任，无法惩罚。而信任梯度是这个平台低人肉运营架构的地基。
- solo 运营下，匿名区是维护成本最高的区域：100% 的治理负担落在站长一个人身上。
- 中文互联网环境下，匿名内容的法律风险由站长独担（这条与"两条生死线"里的版权分级是同一类风险）。
- **东方社区的社交需求是"被认出来"**（画师、翻译、社团、投稿者），不是"藏起来"。匿名反而削弱平台的核心价值——个人主页的作品聚合。

"不想用真名"这个正当需求已经被**自定义显示名 + 头像**完全覆盖了，那不叫匿名。

### 5.3 签名档
- 纯粹的视觉噪音税：每一楼多出三行与内容无关的东西，移动端尤其致命。
- 现代论坛（Discourse / V2EX / linux.do）**全部没有签名档，且这是明确的设计决策，不是遗漏**。phpBB/Discuz 世代有它，是因为那个年代没有用户卡片和个人主页。
- 它是 spam 的载体：签名档挂外链，正好绕过 §3.9 的新账号外链限制。
- 它的正当需求——"我是谁、我做过什么"——已被个人主页 + 头像 + 点头像弹出的用户卡片覆盖，且覆盖得更好。

### 5.4 踩 / downvote
理由见 §3.5：小社区里被踩是可归因的社死；它唯一的价值（内容过滤排序）在内容量为 0 时不存在；而**加它是 additive，撤它不是**——用户已经承受过的体验收不回来。

### 5.5 可见的用户等级与头衔（游戏化）
必须与信任等级区分开：**信任等级（内部权限判断）必须有且已有；可见等级 / 头衔（游戏化激励）永远不做。**
- 激励机制在没有活动的社区里激励不出东西（"等级 2 需要 100 帖"而全站总帖数 30）。
- 它一旦公开就**固化早期用户的地位差**，把后来者永久标记为"新人"——这对一个需要靠新来者活下去的社区是反向的。
- 权威标识（版主/站长 badge，§3.17）是另一回事，那个要做。

### 5.6 敏感词的"变体检测 + 星号替换"那一档
（词表本身要做，见 §3.11。）变体绕过检测与自动打码这两项永远不做：它们的误伤率在东方圈的语料上（角色名谐音、日文汉字、社团名）高得离谱，而**每一次误伤都是一次人肉申诉处理**——恰好是这个平台的架构前提要避免的东西。命中硬红线就直接拒绝，让用户看得见地改，比偷偷打码诚实也便宜。

## 6. M4 唯一真正不可逆的三件事

按方法论，除了对外 URL 和法律留痕，一切"预留"都按 YAGNI 处理。这三件是例外，必须一次定对：

### 6.1 主题的 URL 形状
`/shrine` 现在还是 `routes/stub.tsx`，这是唯一的窗口。三个候选：

| 方案 | 例 | 问题 |
|---|---|---|
| 纯 uuid | `/shrine/t/0193...` | 丑、不可口头传播、SEO 无信息 |
| 版块内序号（NGA 式） | `/shrine/b/tea-party/1234` | 主题移动版块就换 URL；且需要 per-board 计数器 |
| **slug + id（Discourse 式）** | `/shrine/t/主题标题-slug/0193...` | slug 是装饰、id 是权威、slug 不匹配时 301 到正确的。标题可编辑而 URL 永久稳定 |

建议第三种。它是被大规模验证过的最优解，且天然处理"标题可改"这件事。

配套要一起定：**`kind='resource'` 的主题 301 到 `/kourindou/:slug`**（§3.2 子问题 2），规范 URL 唯一。

### 6.2 用户 handle
`user.name` 不唯一、可含空格、随时可改，不能做 @提及的锚点，也不能做 `/u/:x` 的路径段。需要一个独立的、唯一的、字符受限的 handle，并决定：注册时要求还是首次使用时补？允许改几次？（建议：注册时生成可改一次，或首次 @/发帖时强制设置。）

一旦帖子正文里存了 `@某个字符串`、或 `/u/:handle` 对外发出，就改不动了。

### 6.3 内容删除的语义（法律留痕那一类）
M3 的形状是对的，M4 只需守住：**论坛内容一律软删 + `moderationLog` 留痕，硬删只走站长本地脚本**（`deleteResourceSchema` 已有 `mode: 'soft' | 'purge'` 且理由必填的先例）。楼层软删保留占位（`post.ts` 已实现，不要为了"干净"改成硬删——楼层号会出洞、引用会断）。

补一条与引用现查（§3.3）的联动：**因为引用是现查而不是快照，一次软删就能让被删内容从所有引用块里消失**。这是把删除做干净的前提，也是选现查方案的主要理由。

## 8. 对现有 schema 的最小增量（**建议，不是决定**）

按上面的取舍，M4 的数据层增量小得出乎意料——因为 M3 把 `topic`/`post` 按 M4 的形状建好了：

**新表 3 张**（全部是查找表或极简关联表）
- `board`：版块（slug 主键 / 三语 name jsonb / description / sortOrder）
- `post_reaction`：点赞（postId + userId 复合主键，与 `favorite` 同构）
- `topic_subscription`：隐式订阅（topicId + userId 复合主键 + source + muted）
- `notification`：通知（这是第 4 张，但它是产品已批准的模块本体）

**加列 4 个**
- `topic.pinnedAt`、`topic.lockedAt`
- `topic.postCount` / `lastPostAt` 已在，无需动
- `post.likeCount`（冗余计数，与 `resource.ratingCount` 同一模式）
- `user.handle` + 唯一索引（§6.2），或落在 `userProfile` 上
- `userProfile.notificationsSeenAt`

**索引要调 1 个**
- `topic_board_last_post_idx` 现为 `(boardSlug, lastPostAt)` 升序，加了置顶后排序键变成 `(pinnedAt DESC NULLS LAST, lastPostAt DESC)`，需要重建。同时全站最新流需要一个不含 `boardSlug` 的 `lastPostAt DESC` 索引。

对比 M3 的教训——调研 agent 提 28 张表被砍到 13 张——**这里的天花板本来就低，因为地基是对的**。如果谁的 M4 设计里出现了十几张新表，那多半是把 §4 和 §5 的东西塞进来了。

## 9. 遗留给站长拍板的问题

这些我无法自行决定，因为它们要么与已批准决策有张力，要么涉及不可逆选择：

1. **六版块 vs "少开胜过多开"。** 关版块 = 死链（不可逆），开版块 = 零成本。我给的缓解方案是"六个全开但默认视图是全站流"，但更保守的做法是**先开三个（茶话会 / 二创工坊 / 站务），其余三个等有人要了再开**。要不要动这条已批准决策？

2. **handle 的获取时机。** 注册时强制填？允许改几次？还是首次发帖 / 首次被 @ 时才要求设置？一旦对外就不可逆（§6.2）。另有一个连带问题：handle 允许哪些字符——只 ASCII，还是允许日文假名（面向全球、ja 有战略意义，但会让 @ 补全和 URL 编码变复杂）？

3. **邮件通知进不进 M4。** 这是全文唯一一条"推迟有真实代价"的推迟项：冷启动用户不天天回访，邮件是唯一召回通道。但仓库里没有任何发信基础设施。要不要在 M4 就把它连上（连带影响：是否顺手接上 better-auth 的邮箱验证）？

4. **资源讨论主题的版块归属。** 我建议不属于任何版块、只进全站流（§3.2）。但若产品希望"音乐堂"版块里能看到音乐资源的讨论，就是另一套摆法。这个选择影响版块的定位，改起来是查询层的事（不是不可逆），但会影响上线观感。

5. **论坛侧的信任升级路径。** `approvedResourceCount` 现在只由资源审核递增，纯论坛用户永远升不了级（§3.13）。加"有效发帖数"会造出刷帖激励，加"账号年龄"最省事但最粗糙。用哪个？

6. **主题 URL 里要不要带中文 slug。** Discourse 式 `slug + id` 里，slug 若取自中文标题会变成一长串 percent-encoding。是取拼音、取英文、还是干脆只留 id？这条属于 §6.1 的不可逆范围。
