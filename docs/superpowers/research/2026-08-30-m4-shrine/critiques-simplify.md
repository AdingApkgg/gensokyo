1. 上线第一个月它会被用到吗？

> M3 的方法论纠正对本次同样成立，而且必须**双向**使用：
> 空库上「现在不建以后要迁移」不是理由；**同样地，「这个决定不可逆所以现在必须定」也不是理由——不可逆决定的正确处置是「能不做就先不做」，因为不做是可逆的，做了才不可逆。** 设计文档在东方表情（`designs-web` §5.6）这一条上把这条规则用反了。

## 一、可删项

### D1. `board` 表 —— 删（3 份设计里 2 份已经主张删）

**删了失去什么**：`topic.board_slug` 的外键；版块名/说明可以不部署就改。

**正面反驳 `designs-schema` §2.2 的「决定性理由」**。它说：常量方案下 `boardSlug` 永远是裸 `varchar(32)`，任何写路径打错一个字符就产生一条「不出现在版块页却出现在最新流」的孤儿主题。

这个失败模式**在本方案下构造不出来**：

1. `boardSlug` 只有一个写入口（`POST /shrine/topics`），校验是 `z.enum(BOARD_SLUGS)`——一个**闭合的 6 值枚举**，不是自由文本。用户打错不会入库，会得到 400。
2. 唯一能打错的地方是 `BOARD_SLUGS` 常量数组本身。而 `board` 表的六行是**从同一个常量数组 seed 的**——常量里打错了，seed 出来的外键目标也打错了，**外键照样通过**。这条外键挡不住它声称要挡的那个错误。
3. 它真正能挡住的只有「有人手写 SQL 插了个不存在的版块」——而那是站长在故意操作，而且以后想加也是一条 CHECK 的事：`check('topic_board_slug', sql\`board_slug is null or board_slug in ('tea-house', …)\`)`。**零表、零 join、DB 层保证一模一样。**

更要命的是**同一份文档在 §8.1 做了相反的判决**：`report.targetKind` 是 `varchar(16)`、无枚举无 CHECK 无外键，理由写的是「唯一闸门是 zod 那道 `z.enum(['resource','post'])`，不把它升成 pgEnum」。同一份设计，同一种「闭合小枚举 + zod 单一写入口」的形状，两个相反结论。

**理由二（与 `resource_category` 同构）也不成立。** `resource_category` 是**用户在上传向导里选的业务分类**，而版块是**导航 chrome**。真正同构的对象是 `RESOURCE_KIND` / `LICENSE_STATUS` / `MIRROR_KIND`——它们都是固定小枚举，全部是 `packages/shared` 的常量，没有一个建表。

**理由三（描述是运营文案，改字要走部署）被 `designs-web` §6.4 反驳过了，而且反驳是对的**：M4 不做版块管理后台，所以「改 DB 里的名字」的实际操作是 psql 手改 jsonb——比 `git push` 慢、没有 review、没有三语齐全检查（仓库有 `check-messages.ts`，DB 里的 jsonb 不进它的视野）。而 CLAUDE.md 明令「代码里一律 `m.key()`，不写裸字符串」；把 6 个版块名放进 DB 等于给站点开第二套 i18n 机制。

**以后补的代价**：一张 6 行查找表 + 一条 seed + 把 `z.enum` 换成 DB 查询。零迁移（版块数据是自己 seed 的）。**触发条件：第一次想加第七个版块，且不想为它跑一次部署时。**

**顺带删掉**：`topic_board_feed_idx` 里为 board 表 join 准备的部分、`board` 的 `LocalizedText` 双列、`content.ts` 与 `shrine.ts` 的依赖方向讨论（§14 里那段「为什么 board 放 content.ts」整段消失）。

### D2. `topic_subscription` 表 + `subscription_state` pgEnum + `PUT /topics/:id/subscription` + mute + 订阅 UI —— 删

**删了失去什么**：显式「关注/取消关注」按钮、静音一个吵闹的主题、第三方（既不是楼主也不是被回复者）跟踪一个讨论。

**正面反驳 `designs-schema` §5.1**。那一节的三条理由（主键不兼容 / 语义不同 / 需要 `muted` 负状态）**全部成立**——但它们证明的是「订阅不能塞进 `favorite`」，不是「M4 要有订阅」。这是答错了题：文档论证的是 **how**，需要论证的是 **whether**。

`designs-schema` §12 给的 whether 论证是：不建它，「通知中心只剩『回复我』和『@我』，冷启动期日均 0 条，红点从不亮 = 负资产」。

**这条自己拆了自己。** 订阅表在 M4 唯一真正会产生通知的那条路径，是 `designs-notification` §4.8 写的第一行：**建资源时同事务给 uploader 插一行 `watching`**——也就是「我的资源有新评论」。而那条边**不需要表**：

```
topic.kind='resource' → resource.uploaderId     （一次 PK join，行本来就要 join 出来拿 slug/标题）
topic.kind='board'    → topic.authorId          （同一行上，零 join）
```

**订阅表存在的意义，是记录「既不是楼主、也不是被回复者的第三个人也想收到消息」。** 这需要**同一个主题里出现第三个说话的人**——那正是冷启动期不存在的东西。上线首月的 `watchersOf(topicId)` 结果集大小是 `{楼主}`，恒定 1 行，而且那 1 行可以从 `topic` 表本身推出来。

**连带删掉的东西比表本身贵**：
- `subscription_state` pgEnum
- 「回复即订阅」的 upsert，以及它那个**必须是 `DO NOTHING` 不能是 `DO UPDATE`** 的陷阱（`designs-notification` §6.3 用了整节解释，因为写错就是「取消订阅坏了」）
- `watchersOf()` + `LIMIT 500` 扇出上界
- 「白名单 `state='watching'` 不能写 `!= 'muted'`」这条要在每个查询点记住的规矩
- 主题页的「订阅中 ▾」下拉（连带 `popover` 这个 shadcn 组件的一个使用场景）
- 3~4 条 message key
- 1 条路由

**以后补的代价**：一张两列表 + 一个 upsert + 一个按钮。库里没有订阅数据可迁（隐式订阅本来就没有存过行）。**触发条件是可观测且精确的：第一个出现三个不同发言者的主题。** 在那之前，扇出集合字面上就是 `{楼主}`。

**产品文档的 `订阅` 字样怎么办**：产品文档写的是「通知中心（回复/@/订阅/审核结果）」。我删的是**显式订阅这个控件**，不是「主题有新回复时通知相关的人」这个行为——后者仍然做，只是收件人由数据推出而不是由一张表存。这是产品项的**部分推迟**，必须写进计划书让站长看见，不能装作没删。

### D3. 通知折叠：`collapse_key` + `count` 列 + 部分唯一索引 + upsert arbiter + 优先级去重 Map —— 删

**删了失去什么**：「有 37 条新回复」合并成一行；收件箱在高流量主题下不被刷屏。

**正面反驳 `designs-notification` §11 的「绝不砍」**。那里说「砍了收件箱立刻变垃圾场，且已读语义随之崩塌」。

垃圾场的前提是**大扇出**。折叠的成本收益完全由「一次动作产生多少行」决定：

| 场景 | 一次回复产生的通知行数 | 折叠是否必要 |
|---|---|---|
| 设计原案（有订阅表，订阅者 1–20 人） | 1 + N | 有意义 |
| **删掉订阅之后（D2）** | **≤ 2**（被引楼作者 + 楼主，且 `notify()` 去重后常常是 1） | **无** |

也就是说：**折叠的全部复杂度来自扇出，而扇出的全部规模来自订阅。** D2 一旦成立，D3 自动成立。这是本次审查里唯一一条「两个削减互相支撑」的地方，值得单独指出来。

而折叠带来的复杂度是四份文档里最高的，全部是**沉默失败**类：

1. `onConflictDoUpdate` 的 `targetWhere` 必须与部分索引谓词**逐字一致**，否则 PG 报「no unique or exclusion constraint matching」（文档自己警告了两次）；
2. 同一条 INSERT 里两行命中同一折叠行 → PG 21000，所以**必须**有那个优先级去重 Map（文档说这不只是产品规则，是正确性要求）；
3. `createdAt := now()` 冒泡，于是折叠行会**逃出**「全部已读」的 `before` 游标——文档说「这恰好正确」，但这是一个要靠一段注释才能理解的行为；
4. 部分索引谓词含 `read_at is null`，于是「已读之后再来新回复新起一行」——正确，但它是第四条需要写进文档才能记住的性质。

四条性质，服务的是一个上线首月不会出现的场景。**这是全文档最贵的一段 SQL，也是最容易被 AI 后续改坏的一段。**

**以后补的代价**：+2 列（`collapse_key` / `count`）+ 1 个部分唯一索引 + 把 `insert` 改成 `onConflictDoUpdate`。旧行的 `collapse_key` 为 null，而**文档自己说「null = 不折叠，PG 唯一索引里 NULL ≠ NULL，所以不折叠的种类不需要任何分支」**——也就是说，存量数据天然兼容，这是一次教科书级的 additive 升级。**触发条件：第一个让某个人在一天内收到 10 条以上通知的主题。**

**保留 `read_at`**（一列，行级已读）。`designs-notification` §1.1 否决水位线的三条理由里，第一条（折叠依赖 `read_at`）随折叠一起消失，但第二、三条仍然成立，而且行级已读本来就更便宜。

### D4. `post_like` 表 + `post.likeCount` 列 + `like` 通知 + `PUT/DELETE /posts/:id/like` + `recount.ts` —— 删

**删了失去什么**：轻量正反馈；lurker 唯一的表态方式。

**正面反驳 `designs-schema` §7.1**：「5 人在线的论坛里，发帖者收到 3 个赞和收到 0 条回复是完全不同的留存结果，而让这 3 个人各写一段回复不会发生」。

这句话成立的前提是**有 3 个人读到了那条帖**。上线首月稀缺的不是「表态的意愿」，是 (a) 帖子存在、(b) 第二个人读到它、(c) 那个人已登录——三个条件里两个正是冷启动缺的。**点赞不能凭空造出读者。**

上线首月真正撑住「发了帖有人理」的，是**站长逐条回复每一帖**——这是所有论坛冷启动的实际做法，也是 solo 站长确实做得到的事（帖子数量是个位数）。而站长要能做到这件事，需要的是 `reply` 通知，不是点赞。**点赞是站长做不动之后的替代品，不是启动器。**

`designs-notification` §11「若超出预算按顺序砍」把 `like` 排在**第一个**——这份设计自己就把它归为最可弃的一项。

**连带删掉**：`post.likeCount` 冗余计数（文档自己承认它有一个已知的、和 `rating.ratingSum` 同形的删号漂移 bug）、`recount.ts` 脚本、楼层列表里的 `likedByViewer` join（在**全站最热的读路径**上）、乐观更新 + 回滚 + toast（连带 `sonner` 这个 shadcn 的主要使用场景）、`NOTIFICATION_KIND` 的一个值、`collapseKeyFor` 的一个 case、2 条路由、2~3 条文案。

**以后补的代价**：一张两列复合主键表 + 一列计数 + 2 条路由 + 1 个 enum 值。库里没有点赞可迁。**触发条件：第一个星期里出现 10 条以上非站长发的帖。** 这条我承认是本文最接近边界的一刀——如果站长觉得应该保留，它是**唯一一条我不会强烈反对保留的**，但保留它的理由应该是「我想要」，不是「冷启动需要」。

### D5. `topic.lockedAt` + `POST /topics/:id/moderate`（pin/unpin/lock/unlock/move）+ `TOPIC_MODERATE_ACTION` + `topic_locked` 错误码 + 锁定态 UI —— 删（保留 `pinnedAt` 列）

**删了失去什么**：版主在页面上锁帖 / 置顶 / 移动版块的按钮。

**正面反驳**：`designs-schema` §3.2 说 lockedAt 是「两视图整合的必然产物」（资源下架 → 评论区必须停写）。**`designs-api` §1.4 已经把这条论证拆掉了**：可见性白名单联查 `resource.status='published'` 天然挡住了写入，「不需要 `lockedAt` 列，也不需要在下架路径上挂钩子」。两份文档在同一件事上一个说必要一个说不必要，而 api 那份的论证更强（白名单不会漂移，钩子会）。

剩下的唯一用途是**版主锁一个吵起来的版块主题**。上线首月这类主题的数量是 0，而站长处置罕见事件的既定方式，项目里已经有两条先例：**社团认领审批走 SQL**（M3 计划 D7）、**主题/楼层恢复走 SQL**（`designs-api` §2 自己写的）。锁一个帖是 `UPDATE topic SET locked_at = now()`。

`pin` 同理：**六篇引导帖各置顶一次是一次性动作**，一条 SQL 或一行 seed 就够，不需要一个带 reason 校验、审计留痕、三语文案的端点。

`move`（移动版块）：`designs-api` §11.4 主张纳入，理由是「留痕与通知在 M4 恰好都已存在，边际成本是一个 union 分支」。**「边际成本低」不是理由**——同样的话可以对任何一个功能说。移动版块的实际频率是「六个边界模糊的版块偶尔放错」，在 20 个主题的规模下站长一条 SQL 解决。

**保留 `topic.pinnedAt` 这一列**（不保留写它的端点）：`designs-schema` §3.1 给出了这一列的证伪条件——「如果 M4 的计划里没有『发六条引导帖』这一步，这一列应该砍掉」。**见 G1：那一步必须在计划里，而且它是整个 M4 最高杠杆的一件事。** 所以列留，端点不留。

**连带删掉**：`moderateTopicSchema` 的 5 分支 discriminatedUnion、「reason 必填与否」的判据表、`MODERATION_ACTION` 的新值（`topic_lock` / `topic_moderate` 都不需要了——顺带解决了矛盾 #8 的三选一）、`topic_locked` 错误码 + 3 条文案、主题页的锁定态 Alert、置顶徽章的 staff 交互。

**以后补的代价**：1 列 + 1 条路由 + 1 个错误码 + 1 个 Alert。**触发条件：第一次需要锁帖，也就是第一次有两个人在一个主题里吵起来。**

### D6. 游标（keyset）分页 + `packages/shared/src/cursor.ts` + 置顶抽出流外 —— 删，沿用仓库既有的 offset 分页

**删了失去什么**：翻页时不漏帖不重帖。

**正面反驳 `designs-api` §4.1**：「offset 在这里确实会漏帖/重帖，而且是必然的：排序键 `last_post_at` 在每次有人回帖时都会变。」

论证本身正确，**但它需要有第二页才会发生**。上线首月：全站主题总数 < 30 = `TOPICS_PAGE_SIZE`，**根本没有第二页**。而且这个 bug 的表现是「翻页时看到一条重复的主题」——在一个日均 0–3 条新帖的站上，这是所有可能的 bug 里最良性的一个。

代价那一侧文档自己列了，但没算清：`cursor.ts` 的编解码 + 「解码失败必须变成 `validation_failed`，绝不能把用户串喂给 Postgres 的 timestamp/uuid」这条安全要求 + 置顶主题抽出流外的特殊路径 + 部分索引 `(last_post_at DESC, id DESC) WHERE deleted_at IS NULL AND pinned_at IS NULL` + **一条必须写进契约、且客户端必须记住的反直觉规则**：「短页不代表到底，判断是否还有只能看 `nextCursor`」。

顺带一个内部矛盾：那条「短页」规则的理由写的是「`resource.status` 过滤发生在 LIMIT 之后」——**但同一节上方的 SQL 把过滤写在 `WHERE` 里了**（`AND (t.resource_id IS NULL OR (r.status='published' AND ...))`）。SQL 里过滤就没有短页问题。这条契约条款要么是在描述一个不存在的问题，要么在描述一个应该改掉的实现。

**以后补的代价**：`/shrine` 的最新流是**唯一没人会深链第 N 页的列表**（文档自己说的：「没有人深链一个内容会移动的流的第 7 页」）。所以从 offset 换 keyset 时，没有任何对外 URL 会死。**这是罕见的「以后换成本真的接近零」的一项。触发条件：任一版块主题数超过一页，且回帖频率高到翻页期间会重排。**

**楼层区间分页（`?from=137` + 服务端定死 `POSTS_PAGE_SIZE` + 吸附页边界）不在此列，必须做**——见「二、不要删的」。

### D7. 东方表情整条 —— 删（shortcode 词表 · remark 插件 · `EmojiPicker` · `public/emoji/*.webp` · 授权）

**删了失去什么**：产品文档「Markdown + 图片 + 东方表情 + @提及 + 引用」里的第三项。这是本文**唯一**删掉的产品文档明列内容。

**正面反驳 `designs-web` §5.6 自己的两句话**：

> 「⚠️ **shortcode 词表在不可逆那一档**：它会被写进已发布的正文。」
> 「同人图的使用许可本身就踩本站的生死线字段。」

这两句合起来就是删它的完整理由，文档却把它列进了「要做」：

1. **它踩不可逆红线，而删它是可逆的。** 方法论纠正的正确用法是——不可逆决定应当**尽量推迟**，因为推迟是免费的、定错是不可撤的。上线时不做表情，就没有一份要被锁进历史正文的词表。这条规则被用反了。
2. **它踩本站的生死线。** 本站的全部产品前提是「同人作品的再分发许可要标注、要能被认领下架」。为一个装饰功能去用来路不明的同人角色图，是整份文档里风险/收益比最差的一项。做对它要么请人画（一个人 + 预算），要么逐张清授权（一件比本功能本身贵得多的事）。
3. **零帖的论坛不需要表情。** 表情是「已经在热闹聊天的人」用来降低回复成本的东西。

**连带删掉**：remark 表情插件、`:([a-z0-9_+-]{2,32}):` 正则与静态表、`EmojiPicker` 组件、`popover` + `scroll-area` 两个 shadcn 的主要使用场景、净化 schema 里 `img` 的 `['className','th-emoji']` 白名单例外（**这条例外是净化 schema 里唯一一个「允许某个 className」的口子，删掉之后 `'*': []` 全覆盖，安全面更干净**）、4 条文案、`apps/web/public/emoji/` 整个目录。

**以后补的代价**：一个 remark 插件（~20 行）+ 一张静态映射 + 一批图。**触发条件：站长手上有了一批授权明确的表情图。** 在此之前，它是一个既不可逆又踩生死线的决定，而它的收益是「帖子里能插小图」——`![](url)` 已经可以做到。

### D8. `/settings` 页面 + `PATCH /api/me/handle` + `?reason=handle` 拦截 + 自动生成 `u_a7f3k2m9` —— 删，**handle 在注册表单收**

**删了失去什么**：注册后再改 handle 的入口。

**正面反驳**：`designs-notification` §5.1 与 `designs-api` §11.2 都主张「注册时自动生成随机 handle，用户可自选覆盖一次然后锁定」，理由是「冷启动最怕在注册与发帖之间插门」。

**这套设计的用户群是空的。** 逐条推：

- 方案本身规定 handle **自选一次后锁定**。
- 新用户注册后如果去 `/settings` 改，那就是「他本来可以在注册表单里填的那一次」。
- 老用户（种子账号、站长自己）是站长自己的账号，改一条 SQL。

**所以 `/settings` 的真实受众，是「在注册表单加 handle 字段之前就已经注册的普通用户」——这个集合在上线时是空的。** 一个只能用一次、且那一次可以提前到注册表单里发生的页面，就是一个多余的页面。

**替代方案更便宜且更好**：`apps/web/app/routes/register.tsx` 已经存在，加**一个输入框**（`@[________]`，即时校验 `^[a-z0-9][a-z0-9_]{1,19}$` + 保留字）。收益是 handle **可读、可打出来**，而这直接消掉了下一项（D9）。

存量/异常账号的兜底：**从 `user.id` 派生 handle，而不是随机生成再重试**。better-auth 的 id 本来就是 32 位随机串，取前 8 位做 base32 归一 → `u` + 8 位，唯一性直接继承 id 的唯一性，**不需要重试循环，也不需要在 `sessionMiddleware` 这条每请求都跑的路径上处理唯一冲突**。这同时消掉了 `designs-schema` §9.4 花了一整节描述的那个静默死循环失败模式——它是「随机生成」这个选择的产物，不是必然的。

**连带删掉**：1 个页面、1 条路由、`handleSetAt` 列（没有「改一次」这个状态了）、`setHandleSchema`、`handle_taken` 错误码（顺带裁掉矛盾 #10）、`/shrine/new` 的 handle 拦截重定向、`?reason=handle` 分支、7 条文案。

**以后补的代价**：一条 `PATCH` + 一个表单。**触发条件：第一个用户来信说想改名。**

### D9. `@` 补全（`MentionPopover` + typeahead + 用户搜索端点）—— 删

**删了失去什么**：打 `@` 时弹出候选列表。

**正面反驳 `designs-web` §10.2**，它自己已经把这条推理写完了：「自动生成的 `u_a7f3k2m9` 没人打得出来，@ 补全就从『锦上添花』变成『必需品』；注册时收则 handle 可读，补全降级为便利。」

**以后补的代价**：一个 popover + 30 行键盘处理 + 1 条搜索路由。**触发条件：注册用户数上三位数、handle 记不住的时候。**

**连带删掉**：`popover` 与 `scroll-area` 两个 shadcn（配合 D7，这两个组件的所有使用场景都没了）。

### D13. `/shrine` 的双模空态（`total < 10` 自动切换 + 第二个 loader 请求）—— 简化成单一形态

**这一条不是纯删，是用一个更简单的规则做到更多。**

`designs-web` §2.1 设计了一个精巧的双模页面：流为空时整页降级成「六版块引导网格 + 最近 6 个资源横排」，靠 `total < 10` 自动切换。为此需要第二次 loader 请求（`GET /api/kourindou/resources?sort=newest&pageSize=6`）、一个阈值常量、两套渲染分支，以及「失败态与空态必须是两个分支」的额外小心。

**但它是在解一个不该存在的问题。** 矛盾 #11 指出：两份文档对「零回复的资源主题进不进最新流」给了相反答案。裁决应当是 **进**，理由是 `designs-schema` §3.5 说得最清楚的那句——

> 改成 `NOT NULL DEFAULT now()` 之后……**新资源发布即进最新流**……而「资源站给论坛供血」正是这条流存在的全部理由。

`designs-web` §2.1 反对的理由是「一个零评论的资源主题不是『有人在说话』，把它放进『最新』是在稀释这条流唯一的信号」。**在上线当天，那条流没有信号可以被稀释。** 而 M3 已经上线，库里有资源。

于是：**`/shrine` 的最新流从第一天起就不是空的**，双模切换和第二个请求都不需要。页面简化成：

```
顶部：六版块网格（6 张静态卡，纯 chrome，永远渲染，零请求）
下面：最新流（board 主题 + 资源主题混排，按 lastPostAt DESC）
```

一个规则、一个请求、一套渲染。同时 **`designs-web` 那个「版块目录不能当默认视图 vs 六个空版块很难看」的矛盾也消失了**——版块网格不是视图，是页头。

**保留 `designs-web` 那一节里真正重要的两条**，它们与本削减无关且必须做：
- **失败态与空态必须是两个分支**（把加载失败画成「还没有内容」是冷启动期最坏的错）；
- **通知中心的空态必须写清「通知会从哪几处来」**，否则用户学会的是不看它。

### D14. `/u/:handle` 收敛到**一个 tab**；`shrine/layout.tsx` 降级为组件

**个人主页三个 tab（帖子 / 投稿 / 收藏）→ 只留「帖子」。**

## 二、明确不要删的（防止简化过头）

| 项 | 为什么不能省 |
|---|---|
| **`loadVisibleTopic()` / 可见性闸门收口成一个函数** | 四份文档里价值最高的一条，而且它是**净减代码**：仓库里 `createPost` 查 `topic.deletedAt`、`listPosts` 完全不碰 topic 行，闸门已经在漂移。**并且必须采纳 `designs-api` §1.4 那个「函数签名收 `TopicView` 而不是裸 `topicId`」的做法**——让类型系统承担「已过闸」的证明，是这里唯一不靠人记住的机制 |
| **删掉 `/kourindou/resources/:slug/posts`，`/api/shrine` 独占** | 同一张表两个写入口 = 两份可见性判断 = 必然漂移。而且现在改是编译期可发现的重构，M4 之后变贵。裁掉矛盾 #12：`designs-web` §3.1 那段「两边闸门必须不同」的论证以两个端点并存为前提，合并之后不成立 |
| **`topic.lastPostAt` 改 `NOT NULL DEFAULT now()`** | PG 的 `DESC` 默认 NULLS FIRST，不改的话上线当天首页最顶上就是一堆零评论资源。零成本改，不改是首日观感事故 |
| **`postCount` → `floorSeq` 改名** | `postCount` 这个名字字面上邀请人写 `- 1`，而真写了的后果是「该主题从此发不出帖，错误信息却说主题不存在」。三处引用的成本换掉一条走不通的路 |
| **`topic_kind_shape` CHECK + 资源主题不存 `title`** | 在修一个既有 bug：`kourindou/index.ts:194-200` 快照了 `titleOriginal`，既不随 PATCH 更新，又是单语的——把最新流里的资源条目锁死成一种语言，直接违背「面向全球」 |
| **楼层区间分页 + 服务端定死 `POSTS_PAGE_SIZE` + 吸附页边界** | 它**替换**现有的 OFFSET 代码而不是新增，比被替换的更短，且它是 `?floor=137` 深链稳定的前提 |
| **`user_profile.handle`** | M4 唯一同时命中「已对外发出的 URL」与「已发布正文」两条红线的决定，`user.name` 不唯一不可解析。字符集取两个提案的交集：`^[a-z0-9][a-z0-9_]{1,19}$` |
| **@ 提及抽取器放 `packages/shared`，收发两侧共用** | 两边不一致的直接后果是「收到提及但帖子里没链接」。这是类型主轴原则在文本上的应用 |
| **Markdown 管线：react-markdown + rehype-sanitize，坚决不装 `rehype-raw`** | 「不产生 HTML 字符串」这条结构性保证值 55–60KB。**「任何 PR 里出现 `rehype-raw` 都是安全事故」这句话要进 CLAUDE.md**，不是进注释 |
| **净化 schema 里 `className` 不开放、`id` 一律不允许、`'//'` 开头不算站内** | 三条里最容易被漏的是第三条：`//evil.com` 在 `hast-util-sanitize` 眼里没有冒号，会被当相对路径放行，`<Link to="//evil.com">` 会带着 Referer、没有 noopener 跳出去 |
| **图片只放站内 MinIO，外链图降级成链接** | 外链图泄露读者 IP + Referer、随时失效、**且发帖后可以被悄悄换成违法内容而留痕在我们站上**。第三条是治理级别的 |
| **`post.locale` 一列 + `lang=` 属性** | 全文档性价比最高的一项：一列一属性，修掉一个今天就存在的显示错误（日文帖被渲染成中文字形），且不挡住浏览器自带翻译 |
| **发帖限流的前三条**（新账号禁外链 / 冷却窗 / 小时配额） | 仓库里**一处限流都没有**，`rate_limited` 是空悬码。公网上一个开放的写端点会被扫，这与社区规模无关。SQL 守卫（复用 `post_author_idx`、零依赖、跨副本精确）的选型是对的 |
| **`notify()` 是唯一写入口 + 发帖扇出包 SAVEPOINT** | 即使扇出只有 1–2 行也要包：PG 里事务内任何错误都让事务进 aborted 状态，裸 `try/catch` 救不回发帖。且发帖**没有幂等闸门**，重试会发出两楼 |
| **`REPORT_REASON` 加 `spam` / `harassment`** | 现有五值全是资源语义，论坛最高频的两类举报无处可选，举报队列会退化成一堆 `other` |
| **`DELETE /posts/:id` 补 `moderationLog`** | M3 所有 staff 处置动作里**唯一**漏留痕的一处，而产品文档承诺「举报-处理-申诉闭环」 |
| **`createPost` 的 `catch {}` 收窄** | 它现在把唯一违例、连接错误、CHECK 违例一律翻译成 404，闷死了 `post_topic_floor_uq` 这道专为楼层竞态设的告警通道 |
| **`gc-images.ts` 加扫 `post.bodyMd`（逐字子串匹配）** | 不改必炸，且熔断挡不住。`designs-schema` §13.1「不需要解析 Markdown，URL 必然逐字存在，失败方向是多保留」的论证是对的，比建 `post_image` 表好 |

## 三、反向问题：**做得太少，上线就转不起来的地方**

四份文档在「不做什么」上非常克制，但有几处**该做而没有出现在任何预算里**。这几条比上面任何一条削减都重要——削掉的东西以后补是几小时，这几条缺了论坛就是不转。

### G1. **六篇引导帖 + 一篇站规，没有出现在任何一份文档的任务里**

`topic.pinnedAt` 这一列的**唯一**理由是「六版块各钉一条引导帖」（`designs-schema` §3.1 自己写的证伪条件）。但「写那六篇帖」这件事**只作为一列的论据出现，从来没有作为一件要做的事出现**。

这是整个 M4 最高杠杆的一件事，而且它不是代码：

- 六篇「这个版块发什么 / 从这三个话题开始」的引导帖（zh 必须有，ja/en 可以后补——但 ja 有战略意义，产品文档说它是「社团认领通道真正可用的前提」）
- 一篇站规 / 发帖须知（放 `meta` 版块并置顶）——**它同时是举报与处置的依据**，没有它，站长第一次删帖就没有可以引用的东西
- 每个版块的一句话说明（6 × 3 语 = 18 条，D1 之后它们是 Paraglide 文案）

**建议把它做成一条硬前置**：**这七篇文字写不出来，M4 就该推迟而不是开工。** 一个有完整通知系统、完整 Markdown 渲染、完整举报闭环，但六个版块全空的论坛，比一个功能更少但每个版块有一篇像样开场帖的论坛差得多。

### G2. 举报队列显示裸 uuid —— 被列为 P1，实际是 **P0**

`dash/reports.tsx:104,109-111` 把 `targetId` 当等宽 uuid 渲染，没有任何跳转。帖子举报一进来，审核员看到的是一串 uuid，**无法判断、无法跳转、无法处置**。

产品文档承诺的「举报-处理-申诉闭环」在 M4 上线当天就是断的。这是**接线缺口**（`GET /reports` 的 select 投影加 LEFT JOIN），不是新功能，但它必须和「帖子可被举报」同一个 Task 交付。另外 `report.target_id` 是 `text` 而 `post.id` 是 `uuid`，JOIN 要写 `post.id::text = report.target_id`，否则 22P02。

顺带：`reports.tsx:77-81` 的「urgent 优先」是前端 `sort`，**只对当前页有效**，要挪进 api 的 `orderBy`。

### G3. `login` 不支持 `?next=` —— 空论坛里最重要的 CTA 会把人踢回首页

`designs-web` §2.4 发现了，标为「M4 必须顺手改的一处既有路由」。要确保它进计划：**「发第一帖」是整个 M4 唯一真正重要的转化**，登录后回首页等于丢掉这个首帖。

### G4. `gc-images.ts` 的修复**必须排在**帖子插图之前，且 `/api/uploads/image` 至今无限流

两件事，一个 Task：

1. `referencedUrls()` 不扫 `post.bodyMd`。允许帖子插图之后第一次跑 `gc:images` 会精确地删光全部帖子插图，**而脚本头部的熔断挡不住**（封面和头像还在，引用集合非空）。
2. `POST /api/uploads/image` 一处限流都没有。M3 时它只对上传向导开放，实际用量受限；**M4 把它接到每个人的回复框上**，一个登录 bot 可以把 MinIO 填满。`designs-api` §6.2 把它列为「相邻缺口，不在 M4 范围」——**它在范围内**，因为正是 M4 让它变得可达。

**Task 顺序是硬约束**：GC 修复 + 上传限流 **必须先于** 编辑器的图片按钮。

### G5. 资源页 → 论坛的入口不存在

设计里 `/shrine/t/:id` 遇到资源主题会 **301 跳走**到 `/kourindou/:slug#discussion`。方向是对的，但结果是：**资源讨论在 UI 上永远不以「论坛内容」的形态出现**，只作为最新流里的一行。

一个从最新流点进资源讨论的人，落在资源详情页，那里**没有任何一条路通回 `/shrine`**。这条管道现在是单向的，而它是整个 M4 的供血管。至少需要：资源详情页评论区上方一条「在博丽神社查看讨论 / 去神社逛逛」的链接，以及 `SiteHeader` 里 `/shrine` 从 stub 变成真入口。

### G6. e2e 验收没有预算

M3 有 `bun run e2e`（23 项）。M4 只在 `designs-notification` §11 出现过「e2e 加 4 项」一行。以本次的接线量（可见性闸门收口、URL 合并、限流守卫、通知挂点），4 项不够。建议至少覆盖：发主题→回帖→楼层号连续、@ 提及产生通知、资源评论与论坛帖走同一段代码、下架资源后评论区停写、限流触发、举报帖子进队列且队列显示得出上下文。

### G7. 「站长逐条回复」这件事没有被当成机制

D2/D4 都建立在一个前提上：**上线首月的反馈由站长手动提供**。那么站长需要的是「有新帖了」这个信号能立刻到达他，而设计里站长收到的通知与普通用户走同一条路（他只有在别人回他的帖或 @ 他时才收到）。

`designs-notification` §1.2 否决 `mod_queue` 通知的理由（收件人是「当前 staff」，提权降权后指向错的人）成立，它给的替代是「`/dash` 导航上显示待办计数」。**但那个计数只覆盖资源待审与举报，不覆盖「有新帖」**——而新帖恰恰是 M4 唯一需要站长盯的东西。

建议：`/dash` 布局的计数里加一项「今天的新主题/新楼层数」（一个 `count(*)`，与既有的 `GET /moderation/queue` 的 `total` 同形），零表零通知。

### G8. `sessionMiddleware` 的 `onConflictDoNothing()` 在加 `handle` 之后会静默失效

`designs-schema` §9.4 发现了这个（无 target 的 `DO NOTHING` 不区分冲突目标，handle 唯一违例会让 profile 行根本建不成，`returning()` 返回空，且**每次请求都重试并再次失败**）。这条要进计划书的显眼处，不能只留在设计文档里——它是一个「上线后所有新用户都没有 profile 而且没人会立刻发现」的故障。D8 的「从 user.id 派生 handle」让重试循环消失，但 `onConflictDoNothing({ target: userProfile.userId })` 这个显式 target 仍然必须写。

## 五、如果我是站长，我会先做哪三件事

**一、先裁掉那 14 处矛盾，尤其是六个版块的 slug 和 handle 的字符集——在写第一行代码之前。**

四份设计是并行写的，谁也没读谁。两份文档给了两套版块 slug（`tea-party/danmaku-lab/kappa-heavy` vs `tea-house/danmaku/kappa`），两套 handle 正则（一个允许 `_admin`，一个不允许）。**这两样发出去就锁死**——版块 slug 进对外 URL，handle 进对外 URL 和已发布的正文。其余 12 条不裁完，计划书写不了，因为按任意一份实施都会与另外三份冲突。这件事的成本是一个下午，收益是不用在实施到一半时推翻。

**二、把六篇引导帖和一篇站规写出来——真正的文字，不是「待补」。**

论坛冷启动缺的从来不是功能，是内容。M4 的全部技术方案里，只有 `topic.pinnedAt` 这一列的论据提到了引导帖，而「写引导帖」本身没有出现在任何任务清单里。如果这七篇文字写不出来（写不出「弹幕研究所该发什么」，往往意味着这个版块不该存在），**那 M4 该推迟的是开工日期，不是这七篇**。一个功能齐备但六个版块全空的论坛，读到的是「这地方是死的」；一个只有主题、楼层和回复通知，但每个版块有一篇像样开场帖的论坛，读到的是「这里有人」。

顺带，这七篇文字会立刻告诉你版块划分对不对——比任何 schema 讨论都准。

**三、先把「资源讨论进最新流」这一条单独做完并上线，再做其余的 M4。**

它的全部内容是：`lastPostAt` 改 `NOT NULL DEFAULT now()`、资源主题不再快照标题、一个混排的最新流页面、资源详情页的评论区接到同一段 service、以及资源页与 `/shrine` 之间的双向链接。**没有通知、没有 @、没有点赞、没有订阅、没有 Markdown 渲染器，也能上线。**

这么做有三个理由：

- 它是整个 M4 里**唯一一件不做就真的转不起来**的事——「靠资源站供血」这句产品判断的全部实现就是它，其余都是给已经存在的对话加体验；
- 它让 `/shrine` 在上线第一天就不是空的（M3 的资源已经在库里），于是 D13 那个精巧的双模空态、`total < 10` 阈值和第二个 loader 请求全都不需要写；
- 它把风险最高的那个重构（可见性闸门收口 + 删掉资源侧评论 URL）**单独放进一次可回滚的发布**，而不是和通知、handle、Markdown 渲染混在一个大 commit 里——M3 有过未评审的 schema 草稿混进大 commit、最后整个被撤回的先例。

做完这三件，再按 T4–T8 铺其余部分。真到那时你会发现，点赞、订阅、折叠、表情这几项该不该做，已经有数据可以回答了——而现在没有。
