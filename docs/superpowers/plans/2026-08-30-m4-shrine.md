> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 博丽神社可用，且产品文档第 1 号已批准决策**在代码里成立**——资源评论区与论坛帖是同一张表、同一段 service、**同一道可见性闸门**。上线时六个版块各有一篇引导帖，全站最新流从第一天起就不空。

## 范围决策：为什么比设计方案小得多

四份设计合计提出 **4 张新表 / 16 条路由 / 8 个页面 / 118 条文案 / 13 值通知枚举**。
三份对抗审查判定其中大半是为「内容太多」设计的，而 M4 的问题恰好相反。本计划收敛到 **1 张新表 / 11 条路由 / 6 个页面 / ≈75 条文案 / 7 值枚举**。

M3 那条方法论纠正在 M4 必须**双向**使用：

> 空库上「现在不建以后要迁移」不是理由；
> **同样地，「这个决定不可逆所以现在必须定」也不是理由——不可逆决定的正确处置是「能不做就先不做」，因为不做是可逆的，做了才不可逆。**

设计方在东方表情上把这条规则用反了：自己写下「shortcode 词表在不可逆那一档」「同人图的使用许可踩本站生死线」，然后把它列进要做。

| 砍掉 | 理由 |
|---|---|
| `board` 表 | 外键挡不住它声称要挡的错误：`boardSlug` 唯一写入口是 `z.enum` 闭合 6 值，用户打错得 400；唯一能打错的是常量本身，而表的六行是从同一个常量 seed 的。改为一条 CHECK，DB 层保证一模一样，零表零 join |
| `topic_subscription` + mute + 订阅 UI | 它证明的是「订阅不能塞进 favorite」（how），不是「M4 要有订阅」（whether）。唯一真正产生通知的那条边（我的资源有新评论）不需要表：`resource.uploaderId` / `topic.authorId` 就在行上。订阅表记录的是「既不是楼主也不是被回复者的第三个人」——正是冷启动不存在的东西 |
| 通知折叠（`collapse_key` / `count` / 部分唯一索引 / upsert arbiter） | 折叠的成本收益完全由扇出规模决定，而扇出的全部规模来自订阅。删掉订阅后一次回复产生 ≤2 行通知。这是全部文档里最贵、沉默失败最多的一段 SQL，服务的是上线首月不出现的场景 |
| `post_like` + `likeCount` + like 通知 + 2 条路由 + `recount.ts` | **站长已确认删除。**「3 个赞好过 0 条回复」的前提是有 3 个人读到了那条帖，而上线首月稀缺的正是读者——点赞造不出读者。连带消掉计数漂移、最热读路径上的 `likedByViewer` join、以及点赞轰炸这条骚扰链路（而私信/拉黑明确不做，受害者没有屏蔽手段） |
| `topic.lockedAt` + `/moderate`（pin/lock/move）+ `topic_locked` 错误码 | 「资源下架必须自动锁」已被可见性白名单联查拆掉（白名单不会漂移，钩子会）。剩下唯一用途是版主锁一个吵起来的主题，首月频次 0，项目已有两条「罕见 staff 动作走 SQL」的先例 |
| 游标分页 + `cursor.ts` | offset 漂移论证正确，但要有第二页才会发生：首月全站主题数 < 一页。它的表现（翻页看到一条重复主题）是所有 bug 里最良性的 |
| 东方表情整条（词表 / remark 插件 / EmojiPicker / `public/emoji/`） | 唯一被删掉的产品文档明列内容。它既踩不可逆红线又踩生死线（同人角色图的使用许可），而收益是「帖子里能插小图」——`![](url)` 已经做得到 |
| `@` 补全 + 它需要的用户搜索端点 | handle 可读之后补全从必需品降级为便利；那个端点在 16 条路由预算里根本没被计价，还需要枚举防护 |
| `content_blocked` 硬词表 / `duplicate_content` 规则 | 不做变体检测的词表绕过成本是插一个空格，挡不住任何真心要发的人，只误伤正常用户。本站真正的法律机制是举报→下架→`takedown_request`，M3 已做完。15 秒冷却窗已覆盖重复提交 |
| `gc-notifications.ts` / `recount.ts` | 给一张一年内不会超过几千行的表配带熔断、分批 DELETE、双开关的清理脚本。M3 砍 `storage_gc_queue` 用的是同一条判据 |
| `/settings` 页面 | 「自选一次后锁定」意味着它的真实受众是「在注册表单加 handle 字段之前就已注册的普通用户」——上线时这个集合是空的 |
| 通知 kind 13 → 7；个人主页 3 tab → 1 tab | 按「上线首月会不会触发」筛，6 个永远不会亮；「投稿」与 `/kourindou` 列表重复，「收藏」是「我的收藏」页不是主页功能 |

**反过来，这几件不能省**（真正不可逆、修既有 bug、或不做就转不起来）：

- **可见性闸门收口成一个函数 + 一个表达式**——闸门今天已经在漂移，而这是净减代码
- **删掉 `/kourindou/resources/:slug/posts`，`/api/shrine` 独占**——同一张表两个写入口 = 两份可见性判断 = 必然漂移
- **`user_profile.handle`**——M4 唯一同时命中「已发出 URL」与「已发布正文」两条红线的字段
- **`lastPostAt` 改 NOT NULL** + **资源主题不存 title**——两个上线当天必然发生的 bug
- **`postCount` → `floorSeq` 改名**——现名邀请人写 `- 1`，真写了会让该主题永久发不出帖，而错误信息说「主题不存在」
- **`gc-images` 加扫 `post.bodyMd`**——不改必炸，且熔断挡不住
- **发帖限流**——仓库里一处限流都没有，`rate_limited` 是空悬码
- **六篇引导帖 + 一篇站规**——整个 M4 最高杠杆的一件事，而它在四份设计里从未作为一件要做的事出现过

## Global Constraints

沿用 M1–M3 全部约定（Bun、Biome、`.basePath('/api')`、链式 `.route()` 保 `AppType`、Paraglide 三语无裸字符串、`validate()` 而非裸 `zValidator`、错误按 `code` 不返回人类可读消息、`bun run services` 起依赖），另加：

### 六个不可逆项（站长已拍板，动工前定死，此后不得更改）

| # | 项 | 定值 |
|---|---|---|
| R1 | 版块 slug | `tea-house` · `danmaku` · `workshop` · `music-hall` · `kappa` · `meta`。落 `packages/shared/src/shrine/enums.ts` **单一文件** |
| R2 | handle 字符集 | `^[a-z0-9][a-z0-9_]{1,19}$`，纯 ASCII、无连字符、首字符必须字母数字。显示名（`user.name`）完全自由，handle 只是稳定标识 |
| R3 | handle 可空性 | **NOT NULL UNIQUE**。可空会让「没有 handle 的用户」出现在 @解析 / `/u/:handle` / 通知渲染三条路径的每个分支里 |
| R4 | handle 生成 | **从 `user.id` 派生，不随机**：`'u' + 小写后过滤成 [a-z0-9] 的前 8 位`，冲突时确定性延长前缀（+4 位，上限 19），耗尽则 500。**前缀不继承 id 的唯一性，延长逻辑不能省** |
| R5 | 主题 URL | **uuid**。序号会公开主题总数（`/shrine/t/7` 昭告这里只有 7 个主题），正中冷启动失败模式 A。序号是纯 additive 升级 |
| R6 | 东方表情 | **不做。** 消掉一个不可逆决定，而不做是可逆的 |

### M4 特有的硬约束

- **可见性只有一个来源**：`apps/api/src/modules/content/visibility.ts` 的 `visibleTopicWhere()`（表达式，给列表路径）与 `loadVisibleTopic()`（函数，给取单行路径）。**只有函数不够**——函数只能被「取一行」的路径复用，最新流 / `/u/:handle` / 通知收件箱这些列表路径必然各写一遍 WHERE，那正是 P0-1 泄漏的成因
- **`content/post.ts` 的全部函数接收 `TopicView` 而非裸 `topicId`**，让「没过闸就拿不到参数」成为编译期事实
- **`isSelf(actor, ownerId)` vs `isOwnerOrStaff(actor, ownerId)`**：编辑他人正文永远禁止（staff 也不行）。`isOwnerOrStaff` 在仓库里出现 6 次且全部是「作者或 staff」，靠注释防住第 7 次不现实——所以给正确写法一个更短的名字
- **`requireAuth` 永远在 `entityIdParam` 之前**：否则未登录用户能用 400/404 的差异探测资源存在性
- **`floorSeq` 只增不减**：它是序列不是计数。软删的楼层保留占位，展示值按 kind 从它推（版块主题 -1，资源主题不减）
- **扇出的 SELECT 必须在事务外**，写入在事务内包 SAVEPOINT（`tx.transaction()`）。PG 里事务内任何错误都让事务进 aborted 状态，裸 `try/catch` 救不回发帖，只会把失败变成 25P02 这种更难懂的形式
- **任何 PR 里出现 `rehype-raw` 都是安全事故**（写进 CLAUDE.md，不是写进注释）
- **通知不可重算**：`notify()` 的去重只对 `RANKED = {mention, reply}` 生效，不在集合里的行直接入队——否则同批次第二条治理通知被静默丢弃且永久丢失
- **新增任何能返回 `post` 行或 `topic.title` 的端点，必须回答「它用的是哪一份 `visibleTopicWhere()`」**

### 沿用 M3 的踩坑清单（逐条复核过，对 M4 同样成立）

- zod 的 `.partial()` **不移除 `.default()`**，更新用 schema 必须逐字段重建
- id 分三种不可混用：`entityIdSchema`(uuid) / `userIdSchema`(better-auth 32 位串) / `slugIdSchema`
- 状态判断一律**白名单**，绝不写 `!== 'delisted'`
- Hono 的单值 query 是 string，数组参数要 preprocess 升维
- **测试必须接 `apps/api/src/test-support.ts` 的 track/cleanup**——dev 库不是一次性容器
- 每个 Task 结尾 `bun run check:fix && typecheck && test` 通过再提交

## 与产品文档的两处偏离（需要站长知情）

产品文档第 45–53 行定义的 M4 里，有两项本计划**没有完整交付**。两项都不是技术做不到，是判断它们在冷启动期没有收益：

1. **「东方表情」整条删除。** 这是唯一被删掉的产品文档明列内容。它踩两条红线：shortcode 词表一旦对外就在不可逆那一档；同人角色图的使用许可直接踩本站的版权生死线。而它的收益——「帖子里能插小图」——`![](url)` 已经做得到。**恢复条件：站长手上有了一批授权明确的表情图。**

2. **「订阅」部分推迟。** 通知中心的「回复 / @ / 审核结果」三项完整交付，**「订阅」只覆盖隐式的那部分**：楼主与资源投稿者自动收到新回复通知（收件人从 `topic.authorId` / `resource.uploaderId` 推出，不需要订阅表）。**没有显式订阅、没有取消订阅、没有 mute。** 订阅表真正记录的是「既不是楼主也不是被回复者的第三个人」——正是冷启动不存在的东西。**恢复条件：第一个出现三个不同发言者的主题。**

其余产品文档要求（版块式 · 六版块 · 楼层回复 · Markdown · 图片 · @提及 · 引用 · 通知中心 · 举报闭环 · 信任等级共享）本计划完整覆盖。

- [ ] **Step 1: id 与 handle 上提到 `src/ids.ts`**

三种 id schema 现在在 `kourindou/schemas.ts` 里，但 M4 的 shrine 与 notifications 都要用，留在 kourindou 下会造成 `@gensokyo/shared/kourindou` 被 shrine 引用的错位。

```ts
// packages/shared/src/ids.ts
import { z } from 'zod'

// better-auth 的 generateId 产生 32 位随机字母数字串（实测 1.7.2），**不是 UUID**
export const entityIdSchema = z.uuid()
export const userIdSchema = z.string().min(1).max(64)
export const slugIdSchema = z.string().regex(/^[a-z0-9][a-z0-9-]{0,63}$/)

/**
 * handle 是 M4 唯一同时命中两条不可逆红线的字段：它进 /u/:handle（已发出的 URL），
 * 也进已发布帖子的正文（@xxx）。改它等于死链 + 重写历史正文。
 * 纯 ASCII、无连字符、首字符必须字母数字——首字符限制挡的是 _admin 这类视觉冒充。
 */
export const HANDLE_RE = /^[a-z0-9][a-z0-9_]{1,19}$/

/** 保留字。只写在 zod 里的约束绕过 API 就没了，而这里绕过的后果是不可逆冒充 */
export const RESERVED_HANDLES = [
  'admin', 'administrator', 'root', 'staff', 'moderator', 'mod',
  'everyone', 'here', 'all', 'system', 'gensokyo', 'official',
  'support', 'help', 'api', 'me', 'new', 'settings', 'null', 'undefined',
] as const

export const handleSchema = z
  .string()
  .regex(HANDLE_RE)
  .refine((h) => !RESERVED_HANDLES.includes(h as (typeof RESERVED_HANDLES)[number]), {
    message: 'reserved',
  })
```

- [ ] **Step 2: shrine 枚举**

```ts
// packages/shared/src/shrine/enums.ts
/**
 * 版块 slug 进 /shrine/b/:board，是对外 URL——**不可逆**。
 * 关版块 = 死链，开版块 = 零成本，所以方向永远是少开。
 * 不建 board 表：唯一写入口是下面这个 z.enum，用户打错得 400；
 * 唯一能打错的是这个常量本身，而表的六行也是从它 seed 的，外键挡不住它。
 */
export const BOARD_SLUGS = [
  'tea-house',   // 幻想乡茶话会（综合）
  'danmaku',     // 弹幕研究所（原作 STG）
  'workshop',    // 二创工坊
  'music-hall',  // 音乐堂
  'kappa',       // 河童重工（技术）
  'meta',        // 站务
] as const
export type BoardSlug = (typeof BOARD_SLUGS)[number]
```

```ts
// packages/shared/src/shrine/mention.ts
import { HANDLE_RE, RESERVED_HANDLES } from '../ids'
import { MAX_MENTIONS_PER_POST } from './enums'

/** 先挖掉代码块与行内代码，再找 @——否则贴一段含 @ 的代码就会给人发通知 */
const CODE = /```[\s\S]*?```|`[^`\n]*`/g
/** 前面必须是行首或非 [\w] 字符：挡住 foo@example.com */
const MENTION = /(^|[^\w@])@([a-z0-9][a-z0-9_]{1,19})/g

export function extractMentions(md: string): string[] {
  const stripped = md.replace(CODE, ' ')
  const out: string[] = []
  for (const m of stripped.matchAll(MENTION)) {
    const h = m[2]
    if (!h || !HANDLE_RE.test(h)) continue
    if (RESERVED_HANDLES.includes(h as (typeof RESERVED_HANDLES)[number])) continue
    if (!out.includes(h)) out.push(h)
  }
  return out.slice(0, MAX_MENTIONS_PER_POST + 1) // 多留一个让路由层能判超限
}
```
